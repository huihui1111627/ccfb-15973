# 机房备件需求预测与库存策略

一个完全用 Python + NumPy 实现的备件决策工具。**服务器、零件、故障、采购、物流全部是仿真**,
但仿真刻意按真实机房的形态构造:零件故障率随使用年限先低后高、同批次零件故障聚集、
不同型号之间不能替换但存在向下兼容、采购有交货周期、机房之间调拨有运输时间、
老型号会停产需要最后一次采购。

工具从仿真出来的"历史故障记录"里拟合寿命分布、预测未来每月需求,给出每个机房每种备件的
补货点与安全库存,设计"区域中心仓 + 机房前置仓"的两级共享库存,计算停产件的最后一次采购量,
并用同一批故障跑三种策略做验收对比。

```
python3 -m spareparts run             # 生成结果 (约 20 秒, 写入 data/results.json)
python3 -m spareparts serve 8000      # 打开 http://127.0.0.1:8000/
python3 -m spareparts test            # 21 个统计验收测试 (约 45 秒)
```

只依赖 NumPy 和 SciPy;网页端是标准库 HTTP 服务 + 原生 JS/SVG 画图,不加载任何 CDN,
可以在隔离网段的运维机上直接跑。

## 1. 仿真世界(全部在 `spareparts/config.py` 与 `fleet.py`)

| 维度 | 规模 | 说明 |
|---|---|---|
| 机房 | 17 个,8 个区域中心仓 | 北京/上海/广东(3)/四川/湖北/陕西/浙江(3)/山东 |
| 服务器 | 2.77 万台 | 6 种机型,2014–2027 分批采购,23 万+ 台年 |
| 装机零件 | ~58 万个物理位置 | 103 万条"零件在位"记录(含换件) |
| 零件型号 | 15 种 | HDD/SSD/内存/电源/网卡/风扇,含同规格替代料 |
| 采购批次 | 1.9 万个 | 按(机房, 机型, 零件, 半年采购波次)划分 |
| 故障记录 | 截止规划日前 6.8 万条 | 规划日之后的部分不进入估计,只用于验收 |

服务器总数 2.77 万台,仿真期内(2022-01 起)在装约 3.6 万个零件位置,全部历史在位记录 103 万条。

**故障过程**是一个真正的更新过程(renewal process):某位置上的零件失效后,换上一块
**当年采购批次**的新件,新件从实际安装日起重新计时,还会再坏。因此未来需求不是
"今天的存量 × 故障率"的静态衰减,而是"存量的老化 + 换件的再失效"。

**寿命模型**(`life.py`):

```
hazard(t) = 批次质量倍率 × 机型负载 × 机房环境 × [ 随机失效底噪声 + Weibull 磨损项 ]
```

- Weibull 形状 2.0–3.2,尺度按期望寿命标定 → 故障率随年限先低后高(浴盆曲线的右半段);
- 每个批次一个 Gamma 质量倍率(均值 1,CV 0.35–0.9)→ 同批次同波次采购的零件一起早坏;
- GPU 机型负载 1.55×,南方机房 1.05–1.10×,每个机房另有对数正态的"采购质量"差异;
- 10% 的换件是翻新件,故障率 1.8×;
- 服务器按退役计划下线,零件随之下线(右删失)。

**物流与采购**:供应商交期 20–55 天;中心仓到前置仓 0.5–1.75 天;邻区中心仓 1–2 天;
同区机房横向调拨 1–2.5 天;收货统一排到每周的收货窗口。

## 2. 需求估计与预测 (`estimation.py`)

1. **暴露量**。每条"零件在位"记录按年龄段贡献在险件年,截止于失效/下线/规划日。
   存活的零件也计入 —— 少了这一步,寿命拟合会被幸存者偏差拉长。
2. **寿命分布**。按年龄段用 Poisson MLE 拟合 Weibull + 常数底噪声,给出每型号的
   形状、寿命、底噪,并按经验贝叶斯把每个年龄段的风险向参数曲线收缩(数据少的年龄段不会被噪声带跑)。
3. **乘数**。每个型号一个带岭惩罚的 Poisson GLM,同时估计 浏览器型 / 机房 / 批次 三个加性效应。
   共线时惩罚项把信号分摊开,而不是让某个机房去背某个坏批次的锅;批次效应收缩最狠,
   要坏几次才会被认定。
4. **预测**。对规划日之后的每个月做**按月的队列滚动推算**:每批存量按当期年龄算期望失效,
   失效的件以新件身份从当月重新进入(同一台服务器、同一个退役日),服务器退役则整批移除。
   预测区间用负二项,离散度由**滚动回测**(24/12 个月前的起点,预测接下来的窗口)标定 ——
   只用规划日之前的数据,没有前视。

老年龄段的尾部处理:8 年以上观测暴露很薄,直接用 Weibull 外推会高估、把最后一段拉平会低估,
所以取两者对数斜率的折中,并用一个**留出窗口**的经验比值校验。

## 3. 库存策略 (`inventory.py`)

三种策略,同一批故障、同一套交期、同样的仿真期:

| 策略 | 做法 |
|---|---|
| 固定数量备件 | 每个机房压同一份固定配额(按全网络高峰机房定),不看规模差异 |
| 历史均值补货 | 补货点 = 过去 36 个月均值 × 交期 + 教科书式正态安全系数 |
| **两级网络 + 调拨** | 前置仓按**预测分布**定 (R,S);中心仓按 newsvendor 定、持有成本更低;缺货先调中心仓,再调邻区中心仓,再同区横向调拨 |

"每级放多少"不是拍脑袋的参数:对前置仓承担的风险比例与安全库存系数做小网格仿真,
取**满足服务目标(网络满足率 ≥ 97%)的最便宜配置**,网格结果在网页"库存网络"里全部列出。

## 4. 停产件的最后一次采购 (`lastbuy.py`)

对每个停产型号,用同一套滚动推算算到"最后一台载有该型号的服务器退役"为止的总需求,
叠加水平不确定性取 90% 分位作为建议采购量。验收时用**真实故障链**核对:剩余多少、短缺多少。

| 网络满足率 | 98.5% | 96.9% | **100.0%** |

成本口径:持有(资本 + 场地/贬值)、订货、调拨运费、缺货损失(每台服务器每天停机 600 元,
按零件的停机权重折算 —— 风扇/RAID 盘的权重远小于内存)。停产件的一次性采购是三种策略
共同的决策,单独列示,不计入运营成本对比。

**成本结构讲了一个真实的故事**:两级网络用更高的订货与调拨支出,换来明显更低的库存占用和
几乎为零的缺货损失;固定配额策略看似"库存不高",但大量配额压在错误的位置上 —— 小机房堆积、
大机房饿死,于是缺货损失吃掉了全部节省。

## 6. 置信区间校准(诚实的数字)

用规划日之前的数据做滚动回测,名义 80% 区间实际覆盖 **94.6%**,名义 50% 覆盖 **70.6%**,
整体偏差 **−1.3%**。80% 区间偏宽是有意的保守选择:缺货的代价远大于多备一点;
50% 区间偏宽则来自需求的右偏厚尾(已知坏批次 + 计划退役),单一负二项分布无法同时
命中两个分位点 —— 这一点在 `estimate_dispersion` 的注释里写明,并且是验收时公开的数字。

## 7. 网页

```
python3 -m spareparts.server 8000
```

六个页签:

- **总览**:三种策略的对比表、成本与缺货/等待、区间校准;
- **需求预测**:按机房/零件筛选的月度预测与 90% 区间,以及全网络"机房 × 零件"年化需求表;
- **寿命与故障**:每型号的拟合参数与真值对照、故障率随年限的曲线(经验/参数/收缩后)、
  机房与批次乘数;
- **库存网络**:8 个中心仓与所属机房的水位、分级配置的网格选择、机房 × 零件库存热力图、
  库存价值走势;
- **停产件**:采购量、实际尾段需求、剩余/短缺;
- **缺货与调拨**:按策略切换的缺货事件与调拨记录(含运输时间与来源)。

## 8. 代码结构

```
spareparts/
  config.py       拓扑、零件目录、成本与交期、仿真开关(所有可调参数)
  life.py         Weibull + 底噪声 + Gamma 批次的寿命分布;分箱 MLE
  fleet.py        服务器采购波次、批次、更新过程(换件链)、故障与退役
  records.py      截止规划日的 CMMS 导出(在位记录、月度消耗、退役计划、停产清单)
  estimation.py   暴露量、寿命拟合、泊松 GLM 乘数、队列滚动推算、负二项区间、回测
  inventory.py    三种策略的构造与事件驱动仿真
  lastbuy.py      停产件尾段需求与最后一次采购量;真实尾段核对
  acceptance.py   一键跑完并写出 data/results.json
  server.py       只读 HTTP 服务 + JSON 接口
web/              index.html / style.css / app.js
tests/            21 个统计验收测试
```

所有结果都从一个 `Config` 派生;`Config.fingerprint()` 会出现在页面页脚,
种子相同则结果完全可复现。

## 9. 已知的取舍(写清楚,而不是藏起来)

- **50% 区间偏宽**(实际覆盖 70% 而非 50%)。需求是右偏厚尾的:已知坏批次和计划退役让
  某些机房月份异常高。负二项只能有一个离散度参数,对齐 80% 分位就会让 50% 分位偏宽。
  这里选择对齐 80% —— 安全库存和补货点都由它决定,而 50% 只用于展示。
- **老年龄段(8 年以上)的尾部**。观测暴露很薄,直接用 Weibull 外推会高估、拉平会低估,
  取对数斜率折中,并用留出窗口校验。停产件的建议采购量按需求水平不确定性的 90% 分位取,
  所以多数会剩下少量 —— 这是刻意的:停产后缺货只能靠替代料或提前退役服务器。
- **一次性最后采购不计入运营成本对比**。三种策略面对同一份采购量,把它摊进运营成本会
  淹没策略之间的真实差异;它单独列示,并按真实尾段需求核对剩余/短缺。
- **停机惩罚按零件权重折算**。风扇、RAID 盘、冗余电源不会让整台服务器下线;内存、非冗余
  网卡会。权重写在 `config.DOWNTIME_WEIGHT`,是可以替换的假设。
